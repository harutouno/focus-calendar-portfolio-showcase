# 設計判断

## 1. 共有カレンダーの権限を RLS で保護する理由

共有カレンダーでは、複数ユーザーのデータが同一テーブルに格納されます。
権限判定をクライアント側のみに置くと、判定を経由しない経路が発生した時点で保護が失われます。
判定箇所は画面、API ラッパー、オフライン同期、追加実装の各所に分散するため、
保証範囲をクライアント側で維持し続けることは困難です。

判断理由: 権限の正本を PostgreSQL の Row Level Security に置き、保証点を 1 か所に限定するため。

- クライアント側の権限判定は UI 制御を目的とし、権限の保証には用いない
- 判定を除いた場合でも、データベースが他ユーザーの行を返さない
- 招待・受諾・退出のように本人のみが実行できる操作は `security definer` の RPC に限定し、
  テーブルへの直接書き込みを許可しない

検証内容: 所有者・メンバー・第三者の 3 ユーザーを作成し、第三者について
一覧取得・閲覧・編集・招待発行・メンバー操作が成立しないことを、ローカルの使い捨て
データベース上で実測しています（18 項目・全通過）。

制約として、RLS が USING 句のみのポリシーの場合、権限のない UPDATE は
0 行更新かつエラーなしで返ります。このため `if (error) throw` のみでは失敗を検出できません。
`writeEffectAuthority.ts` で影響行数を確認し、成否を判定しています。

## 2. Demo AI を採用する理由

外部 LLM の呼び出しには API キーが必要です。リポジトリにキーを含めることはできず、
環境変数へ委ねた場合はレビュー時に各自のキーを用意しなければ動作しません。

判断理由: 追加の資格情報なしで動作確認できる状態を維持し、
安全に再現可能なレビュー範囲へ限定するため。

`DemoAIService` を唯一の実装とし、端末内で固定サンプル応答を生成します。
Supabase Edge Function 経由で外部 LLM を呼び出す実装は Portfolio Edition から削除しており、
切り替えフラグも保持していません。

設計上の確認対象は応答内容ではなく、AI 出力をアプリのデータモデルへ取り込む境界です。
外部 LLM へ差し替える場合も同じ境界が必要になります。

- `convertAiScheduleToNormalEvent` を変換の唯一の入口とする
- 変換できない提案は例外ではなく `null` を返し、保存経路へ渡さない
- 保存前に確認ダイアログを表示し、AI 出力をユーザー確認なしで永続化しない
- 保存は通常の予定作成と同一の `saveEvent` を通り、AI 専用の保存経路を設けない
- 追加先はベースカレンダー（`BASE_CALENDAR_ID = "main"`）に固定し、
  共有カレンダーへは書き込まない（共有先の選択をユーザーの明示操作に残すため）

## 3. 広告・課金導線・退会を対象外とする理由

判断理由: いずれも動作確認に外部サービスの資格情報または契約が必要であり、
レビュー環境で再現できないため。安全に再現可能なレビュー範囲へ限定する目的で対象外としています。

| 機能 | 必要となる外部要素 |
|---|---|
| 広告 | AdMob の SDK と広告ユニット ID。ID は配信環境に紐づく |
| 課金導線（ストア購入・レシート検証） | ストア課金とエンタイトルメント管理。検証に課金環境が必要 |
| 退会処理 | Supabase Edge Function 3 本と service_role キー |

添付画像は当初この対象外リストに含めていましたが、Supabase Storage のみで完結し
外部の有料サービス・資格情報を必要としないため、後日追加しました（4 章参照）。

プレミアム資格（`user_entitlements` テーブル・`is_premium_active_for()` 等の RPC）の
DB 層も同じ理由で追加済みです——資格を判定するテーブル・RPC 自体は外部サービスに
依存しません。ただし、資格を実際に `premium` へ変更する手段（ストア購入・レシート検証の
UI）はこのリポジトリに含まれないため、この判定は常に `free` を返します。
共有カレンダーの上限（3 件）・マイカレンダー上限等はコードとしてはプレミアム分岐を
持ちますが、実質的には free 固定のまま動作します。

除外の方針として、空のスタブは残していません。
呼び出されても何も行わない関数が残ると、実装済み機能との区別が付かないためです。
呼び出し側を含めて削除し、機能が存在しないことをコード上で示しています。
例外は Demo AI のみで、README・画面表示・コード内コメントの 3 か所に明示しています。

## 4. 互換用 migration の構成

判断理由: 本体の migration を可能な範囲でそのまま保持し、
Portfolio Edition による差分を追跡可能な単位に分離するため。

| ファイル | 目的 |
|---|---|
| `0007_portfolio_compat_account_write_allowed.sql` | 退会機能（本体の 0020）を対象外としたことで未定義になる `account_write_allowed()` を再定義する。無条件に true を返す実装にはせず、null の拒否と実在ユーザーの要求は元実装の条件を維持している。番号は 0007（本体の 0002/0003 は添付ファイル追加に伴い本体と同じ内容を収録したため、空いていた枠へ移動した） |

添付画像を追加した際、本体の `0003_avatar_and_cover.sql`（Storage バケット・RLS・
`update_calendar_cover` RPC を含む完全版）をそのまま収録できるようになったため、
それまでの `0003_portfolio_compat_display_columns.sql`（カラムのみの簡略版）は不要になり削除しました。

`0011_pending_invitee_calendar_cover_read.sql` は収録していません。本体側でも
「レビュー後にユーザー自身が実行する」という未適用の migration として保留されているため、
本体に存在しない機能を Portfolio Edition だけが先取りする形を避けました。この不在の影響は
限定的です——保留中（未承諾）の招待カードだけがカバー画像を表示できず既定の色丸表示になり、
承諾後の通常表示・権限には一切影響しません。

移植時に、PostgreSQL 18 未満で動作しない実装を 1 件修正しています。
招待トークン生成が `encode(..., 'base64url')` を使用していますが、
`base64url` は PostgreSQL 18 以降の機能です。
ローカル Supabase（PostgreSQL 17）で招待発行が実行時エラーになるため、
`translate(encode(..., 'base64'), '+/=', '-_')` へ置き換えています。
乱数のバイト数（24 バイト）は変更していないため、トークンの強度は同一です。

## 5. 「後始末の失敗」を「本処理の失敗」に混ぜない（`runPostPrimaryStep`）

CSV 書き出し（`focusCsvExportService.ts`）は、共有シートを閉じた後に一時ファイルを
削除します。この削除を素朴に `finally { file.delete() }` と書くと、次の 2 つの誤りが起きます。

- 共有が成功していたのに、削除だけが失敗すると「CSV出力に失敗しました」と表示される
  （実際には共有済みなのに、失敗として報告される）
- 共有が失敗していた場合、削除の失敗が元の（真の原因である）エラーを上書きしてしまう

原因は、「本処理が確定した後の、後始末という別の作業」と「本処理そのもの」を
同じ try/catch で扱っていたことです。後始末の失敗は本処理の結果を変えてはいけません。

この形の欠陥は 1 か所だけではありませんでした。カレンダー削除後のカバー画像削除、
共有カレンダー削除後の表示設定クリーンアップ、添付ファイルの正式登録後のドラフト
一時ファイル削除——同じ構造の箇所が複数の画面・サービスに分散していました。1 か所ずつ
個別の if/catch で塞ぐと、次に同じ構造の処理を書いたときに同じ欠陥を繰り返します。

そこで `src/utils/postPrimary.ts` の `runPostPrimaryStep` に 1 か所だけ切り出しました。
意図的に極めて薄い設計にしています。

- 包んでよいのは「本処理が既に確定した後の、二次的な 1 ステップ」だけ
- 本処理そのもの・本処理より前の検証は絶対に包まない（そちらの失敗を握り消さない）
- identity 失効などのセキュリティ判定も絶対に包まない（呼び出し側で別に確認する）
- 失敗は開発時の console.warn にのみ出し、UI 文言は生成しない
- `label` 引数を必須にし、「どのステップを吸収したか」を毎回明示させる
  （名前のない catch-all にしないための強制）

`runPostPrimaryStep` は現在、次の 4 か所で使われています。カレンダー削除後のカバー画像後始末・
共有カレンダー削除後の表示設定クリーンアップ・CSV 一時ファイル削除・添付ファイル正式登録後の
ドラフト一時ファイル削除（`src/hooks/useEventAttachments.ts`）。最後の 1 つは、この関数を
作った後に**別の場所で同じ構造の欠陥が見つかり**、個別の対処ではなくこの関数へ揃えることで
直したものです——1 度直した設計を、2 度目に見つけたときも流用しています。

一度、「この種の欠陥はここだけ」と結論づけていたものが、調査範囲を広げたときに
同じ構造の欠陥が別の場所にもあると判明し、その結論を撤回したことがあります。
呼び出し側の見た目（await した後に確認処理がある、という形）だけでは、
実際に失敗が本処理へ伝播するかどうかは判断できません。呼び出し先の実装を実際に
読まないと分からないというのが、この過程で得た教訓です。
